# SE-3 — shipping the WAL, and reclaiming the disk

Generated by `run_shipping.py`. `run_wal.py` ends by saying the WAL
*bounds the loss to what has not yet shipped* and *does not replace
shipping*. Both were promises about code that did not exist —
`DurableAuditLog.drain()` moved records between two Python lists, and
nothing ever deleted anything, so the log grew forever and "shipped"
meant nothing a crash would respect.

**4,799 + 1 = 4,800** — every decision either reached the sink or was
routed as poison. None was dropped.

Watch the disk column through cycles 4-5-6. The sink is down, nothing
ships, nothing is deleted, and the log grows — **an unavailable sink
costs disk, not data**, which is the entire point of a write-ahead log.
When the sink returns, the backlog ships and the space comes back.

## Why truncation is a delete and not a rewrite

The obvious implementation — read the records, drop the shipped ones,
write the rest back — has a window where the old file is gone and the
new one is incomplete. Crash there and you have lost **every** record,
including the unshipped ones the exercise was supposed to protect.
Rewriting an append-only log to make it shorter converts a durable
store into a lossy one at exactly the moment it is most full.

So the log is segmented. Truncation deletes whole segments in which
every record is acknowledged. A delete is atomic in a way a rewrite is
not: the segment is either there or it is not, and the segments around
it are untouched either way. The **active** segment is never deleted —
it is still being appended to, and removing it would take records
written after the watermark was computed.

## The ordering, which is the whole correctness argument

| order | crash in between costs |
|---|---|
| **watermark first, delete second** | segments the watermark says are shipped stay on disk. The next pass re-ships them and the sink dedupes. **Cost: a duplicate delivery.** |
| delete first, watermark second | records deleted with nothing recording they were ever shipped. **Cost: a decision the firm made about a customer's money, with no trace.** |

`tests/test_shipping.py` executes the wrong order and measures the
loss, rather than asserting the right one works — because an ordering
rule that is only a comment gets simplified away later by someone who
finds it arbitrary.

At-least-once with a durable watermark is the correct trade, and it is
**only** correct because the sink is idempotent on `decision_id`. That
is a constraint on the sink, invisible from the sink's side, so it is
asserted from the shipper's tests. A shipper built on a non-idempotent
sink cannot use this ordering and has no safe alternative.

## The poison record

One record the sink will never accept. Retrying it forever blocks the
watermark, the WAL never truncates, and the disk fills up because of a
single malformed row — a availability incident caused by one bad
record.

So a permanent rejection is distinguished from a transient failure. On
a permanent one the batch is retried **record by record** to find the
poison rather than condemning its ninety-nine innocent neighbours, and
the offender is marked acknowledged so it stops blocking — which is
only acceptable because it is handed to the caller in `shipper.poison`.
Dropping it silently would be the actual bug.

## What this still does not do

- **The sink is in-process.** A real one is a network service, and
  every interesting failure it has — partial batch acceptance, a slow
  response that later succeeds, an ack lost on the return path — is a
  network failure this cannot produce. The retry logic here is
  structured for those and tested against none of them.
- **The watermark is a set of ids, not an offset.** That is honest at
  this scale and does not survive volume: the file grows with every
  decision ever shipped. A production watermark is a per-segment high
  water mark, so it stays constant-sized. Changing it is not hard and
  is not done, because pretending the current one scales would be the
  claim worth avoiding.
- **No compaction.** Segments are deleted whole or kept whole. A
  segment holding one unshipped record among thousands stays entirely.
- **Single disk.** A disk that dies takes the unshipped tail with it.
  The WAL bounds that loss to the shipping interval and does not
  eliminate it.
